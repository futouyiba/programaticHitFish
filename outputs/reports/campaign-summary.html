从 267 种鱼到 28 个逻辑模板

我们想知道：让每条鱼「像那条鱼」地活动，游戏需要写多少种不同的逻辑？ 跑完全库——267 种鱼、295 个行为故事、303 项逐鱼重推——答案是： 28 个可调参的程序骨架，外加一套「怎么得出 28」的可复核方法。

267种鱼全量调研（10 批全过审）
295行为故事全部消费（基线实测）
28活逻辑模板（registry v10 终态）
~70轮独立审核 · 10 版零回滚

01中鱼逻辑是什么——三层流水线

一条鱼每个时刻的行为由三层程序决定。分群路由先回答「它现在处于什么状态」（护巢期？常规觅食？），把它的行为份额分给对应的组；烘焙（Bake）回答「它分布在钓场哪些格子」；响应（Response）回答「饵来了它咬不咬」。

烘焙层的核心语义叫渐进累积：判断链一步一步走，每一步给当前权重乘一个系数——没有单独的「合并」步骤。

三档系数。例子：一条鱼查「觅食水层」——最适应带不折损；差一点的带 ×0.4 还能继续查结构、温度；完全不对的带 ×0.01 立刻结束这个格子的评估。

weight = 1.0
第1步 水层   最适应 → ×1.0 继续
          可接受 → ×0.4 继续
          不居留 → return weight × 0.01
第2步 结构   …同样三档
第3步 温度   …同样三档
（没有第4步「合并」——乘法边走边完成）
return weight

一条链的全部语法。不同鱼的差异＝①因子的集合 ②因子的先后顺序 ③门的类型与位置——这三个差异正是模板分类的判据。

02两次「平铺化」危机——这次战役最贵的教训

普查差点得出一个错误的好消息：「所有鱼收敛得很好，模板很少」。真相是被我们自己拍扁了——而且拍了两次。

第一次平铺（伪脚本层）

早期的鱼表达文件把判断写成了「读因子→查表→合并」的平铺结构：先查什么后查什么的信息全部丢失。用这种输入做普查，61 条鱼里有 61 条被误并进一个大族——「收敛」是假的。

修正：213 份表达文件全部重写为有序 early-return 链（211 份实际修复）；重跑普查一次性拆出 11 个新族，曾被立案的「饱和」结论被证伪。

第二次平铺（约定序冒充推导）

四种鱼的栖息面看起来「顺序完全相同」——后来发现那份相同来自模板的默认约定顺序，不是逐鱼推导。证据里根本没有「谁先谁后」。

修正：终局重跑对每条鱼从形态/生态证据重推顺序——四条鱼各奔四方（蓝鳃结构先行、食人鱼时段被证据直接砍掉）。原候选族撤案，换成 4 个独立新形。

由此立下的铁律（用户裁决）：①顺序就是族判据——因子顺序不同＝不同模板，不得合并；顺序证据不足必须挂起，不许套约定序，也不许虚构。②没有合并步——乘法逐步完成；不居留＝×0.01 软出局而非归零。

03最大发现：一对镜像

把顺序当真之后，全库最大的两个模板自己浮出来了——它们用的是同一对因子，只是先查谁不一样：

镜像对（SPACE_FIRST 61 / FORAGE_FIRST 34）。三批终局重跑独立推导、不同鱼群撞出同一对形状——这是「顺序当真」最有力的回报。两族合计 95 个成员，占全库烘焙程序的三分之一。

06结果为什么可信——每一步都有人挑错

每个批次的固定环路。审校者是上下文隔离的独立 agent，只认工件不认作者——连协调者自己的失误也被抓过两次。

~70轮独立审核
~40轮修复
0registry 版本回滚
0未审突变入册

审校抓过的代表性错误：凭记忆转写的「引文」（冻结证据里不存在）、把「同代号」当「同一种鱼」（淡水白鲳≠红腹食人鱼）、生成器把程序级计数填进「族数」列（连续三批）、修复文本抄错 reviewer 给的算术分解——每一类错误都已沉淀为判例，写进审核角色的长期记忆。

盲纪律也是可信度的一部分：普查的每一步都是「先凭故事盲写出程序骨架并冻结（带哈希），然后才允许打开模板库比对」——防止照着答案填问卷。

07这对游戏意味着什么

做一条新鱼，不需要写新逻辑。

策划的工作变成三件事：①从 28 个模板里挑一个（手册一页一个，中文伪脚本+配置表）；②填参数（因子档位成员、锚形式、衰减系数——全在 Profile 层，不冻结）；③特殊故事进分群路由。鱼的多样性来自参数差异，不是逻辑差异——这句结论从「直觉」变成了「267 种鱼逐条验证过、每一步可复核」的事实。

尚存的开放项（均已在案）：两个单成员 PROV 族待补证；2 尾鱼顺序证据不足挂起待调研线；护巢面的「目标特异性」轴留给机制侧；census↔live 的全面对账（含 284 条负证据台账）是下一段工作的入口。
